# Windows / Android 首版

本版提供 Windows 数字控制台与原生 Java Android 接收端。Python 3.11、3.12 已在 Windows 测试；3.13 纳入 CI 矩阵，未在本机重复执行。APK 最低 Android 10（API 29），编译与 target SDK 为35。Android 16 可以安装该 target 的应用，但不等同于完成真机兼容验证。

Android 配套 APK 1.1.2 保持协议1，新增读取、处理和写回的分段耗时及历史错误关联信息。电脑端版本仍为1.1.0，当前错误报告标记为 `PC diagnostics=4`。本次会话恢复与运动速度修复只修改电脑端，不需要更新1.1.2 APK；1.1.1仍可连接，但完整手机分段诊断需手动用菜单10更新APK。

验收设备：荣耀 Magic5，Android 16 / MagicOS 10。曾在自动化真机复测中完成120秒移动、切换和两次重启高德、恢复指令回执，用户当时确认位置点移动。但后续用户手动操作仍在第53条指令复现超时，因此稳定性验收未通过，当前继续定位。按用户要求，后续由用户手动测试，不再自动操作手机或结束／重启高德。

最近一次用户手动测试反馈：使用谷歌地图时，各项表现看起来正常。该反馈针对谷歌地图当前测试流程，高德曾出现的跳变与延迟原因仍未确认。

## 本机开始使用

1. 安装 Android SDK Platform-Tools，将 `adb` 加入 PATH；Windows 需要手机对应的 USB 驱动。手机开启开发者选项与 USB 调试，用数据线连接、解锁并允许此电脑调试。`adb devices -l` 应显示 `device`，不能是 `unauthorized` 或 `offline`。
2. 双击项目根目录的 `CampusRoute.cmd`。首次需 Python 3.11—3.13，会在 `.venv` 安装项目；不需要 Apple 软件。已经安装的 ADB 也可通过 `CampusRoute.ps1 -Adb '完整路径\adb.exe'` 指定。
3. 首次选择菜单10，回车使用 `build/android/CampusRoute-debug.apk`，或粘贴其他构建出的 APK 路径。手机可能要求确认通过 USB 安装。
4. 选择7设置路线、8设置配速和距离，再选择1连接手机。控制台会打开手机上的接收端，并等待最多90秒。
5. 手机在开发者选项中选择 CampusRoute 为模拟位置信息应用；打开系统定位，点击“允许定位权限”。回到应用点击“启动接收”。权限授权不会自动替用户选择模拟位置应用。
6. 电脑显示“起点已准备”后，选择2开始、3暂停、4中止、5恢复、0退出。手机通知与应用中也有“停止并恢复”入口。

每次新的电脑连接会生成一次性会话，必须在手机点击启动接收。不用菜单1直接从桌面启动 APK 时，应用只显示准备说明。

ADB 查找顺序：显式 `--adb`／启动脚本 `-Adb`，然后项目内 `work/android-sdk/platform-tools/adb.exe`（非Windows为 `adb`），再检查 PATH、`ANDROID_HOME` 和 `ANDROID_SDK_ROOT`。可将 [Google 官方 Platform-Tools](https://developer.android.com/tools/releases/platform-tools)直接解压到上述目录，不需要替换 Unity 或其他软件自带的 SDK。首次切换版本时，结束当前定位会话，用选定的ADB执行 `kill-server` 和 `start-server`，使实际后台服务也使用新版本；这会断开其他ADB连接，请在没有其他调试任务时进行。

## 安装被手机拒绝

`INSTALL_FAILED_ABORTED: User rejected permissions` 表示手机安装器取消或拒绝了安装请求；仅凭这条信息不能区分手动拒绝、确认超时或系统安装限制。菜单10现在会显示处理提示并返回菜单，不会退出整个程序，也不会自动重复安装。

重试时保持手机解锁、亮屏，留在安装确认界面，按手机提示允许安装 CampusRoute。安装确认与USB调试授权是两个步骤。若仍没有安装界面，可以把 `build/android/CampusRoute-debug.apk` 复制到手机，在手机文件管理中打开并按提示安装；手动安装成功后，电脑直接选择菜单1即可。

如果手动安装提示来源权限问题，可在荣耀设置中搜索“安装外部来源应用”，按提示授权实际打开APK的文件管理应用或浏览器。对应官方说明见 [荣耀：无法安装应用程序或安装失败](https://www.honor.com/cn/support/content/zh-cn00406756/)。系统设置名称可能随版本变化，不需要为此关闭全局安装检查或设备管理策略。

## 构建 APK

APK 不要求 Python 或第三方运行库在手机中运行，也不需要 Google Play 服务。项目提供标准 Gradle 工程，可用 Android Studio 打开 `android/`（JDK17、Gradle8.9、Android Gradle Plugin8.7.3）。

已有 Android SDK 的用户也可以完全离线构建，无需下载 Gradle/Maven 依赖：

```powershell
python tools/build_android.py --sdk '你的Android SDK路径' --java-home '你的JDK路径'
```

需预先安装 `platforms;android-35` 与 `build-tools;35.0.0`，JDK建议17或21。本机使用现有 JDK27、SDK35 成功编译并验证签名。输出为 `build/android/CampusRoute-debug.apk`。编译脚本只写入项目的 `build/android/`。

脚本第一次在同目录创建本地调试签名 `debug.keystore`。保留它才能在同一台手机覆盖安装后续版本。不要将这个调试密钥用于正式发布。CI 的调试密钥每次生成，下载不同运行的 APK 时可能需先卸载旧版本；卸载后还需重新授权。Gradle 与脚本默认使用不同调试密钥，切换构建方式亦同。

## 通信与故障处理

菜单11新增可选的配速与轨迹波动，默认关闭，电脑端即可实现，不需要更新APK1.1.2。初始幅度为配速±5%、横向最大0.6米，允许分别设置为0；上限分别为20%与3米。开启后，以多组随机周期和相位的平滑波形生成变化，单次会话内连续，暂停时冻结活动时间，每次新连接重新生成。速度按即时配速计算并保持2:00／公里下限，里程对速度积分；终点按积分求到达时刻。横向偏移使用原路线附近的平滑方向计算，闭合接缝与开放路线折返不翻转偏移。目标里程仍是原路线的前进里程，未把横向偏移额外产生的几何长度加入目标。横向限制仅相对路线，无法保证符合现场跑道边界。

- Windows 只选择 USB 真机；模拟器、无线 ADB 目标暂不作为控制台连接目标。
- ADB 为指定序列号建立动态本地 TCP 转发，手机服务仅监听 `127.0.0.1:47653`，不暴露局域网端口。
- Android TCP 的连接、收发改为在线程中执行阻塞 socket I/O，控制台仍使用 asyncio 调度。回执继续逐条校验；取消或超时时先 shutdown socket 以唤醒接收线程，再关闭缓冲文件和移除本次转发。取消连接时，工作线程迟到建立的socket也会关闭。
- UTF-8 JSON Lines 协议，版本1；握手包含48位十六进制随机会话值。每条指令有递增编号，位置更新和清理均需手机回复。
- 每条指令等待回执最多3秒。超时、无效回执或序号不符时关闭当前socket，避免迟到的旧回执被当成下一条指令的确认。此类会话错误现在会显示完整诊断、尝试清理并返回菜单，保留路线与设置；不会退出整个电脑端，也不会自动重连或继续移动。清理错误单独提示，不覆盖最初的通信故障；即使清理失败也释放旧会话引用，允许菜单1重新连接。关闭连接后手机尝试清除模拟位置，未收到清理确认时电脑仍提示使用手机“停止并恢复”。
- 截止时间使用 `perf_counter` 高精度时钟。计时器提前唤醒时重新核对剩余时间，不取消当前收发操作；截止时若工作线程已经在期限内收到完整一行，而结果通知仍排队，则取得该行继续正常校验。真正超过截止时间收到的行和未完整收到的行仍按超时处理，不重发位置指令。诊断中的 `boundary_recoveries` 与上次回执的 `deadline_boundary_recovered` 标明这条恢复路径是否发生过。
- Python 沿用 WGS84 路线计算，约每0.2秒发送位置；不为每个坐标启动 ADB 子进程。手机添加 GPS / network 测试位置提供器，填入时间、精度、速度和朝向。
- 控制台约每秒刷新累计距离、移动用时、手机已确认坐标及已发送的速度／朝向，刷新在成功收到位置回执后执行；暂停时距离和用时保持不变。Windows cmd 启动时启用终端光标控制，原地更新状态区域，保留菜单输入。
- 运行时按所选配速（开启波动时为即时配速）发送速度，朝向取偏移后轨迹前方约0.5米方向，不再用两次发送位置之间的距离／间隔推算运动速度。准备起点、暂停、中止、到达目标时显式发送速度0。菜单3、4在最后已确认的路线位置立即发出静止定位，并等到回执后才显示操作成功；不会先补算等待上一条回执期间的移动距离。已排队的菜单指令先于下一次周期定位处理；已经发出的指令仍需等回执或超时，不能撤回。之后继续刷新同一静止位置。
- 连续5秒未收到完整指令、socket断开或服务正常停止时，手机尝试移除测试提供器。移除失败会显示错误，不报告恢复成功。
- 电脑显示“手机已确认坐标”仅表示 Android 定位 API 调用成功且回执匹配，不能替代系统回读或目标应用实测。
- 手机上的前台通知在接收期间保留；定位期间使用短期、持续续期的 CPU 唤醒锁。电脑控制台运行时请求 Windows 保持唤醒。电脑主动休眠、USB中断或厂商强制回收仍可能结束会话。
- MagicOS 若在锁屏后中断接收，需要检查该应用的后台运行和电池管理设置；具体行为以真机测试为准。
- Android 标准模拟位置带有模拟标记。不同应用，特别是使用厂商融合定位的应用，是否采用 GPS / network 测试位置需要分别验证。

旧版的“Android 回复序号不匹配”可能由超时后的清理引发：例如位置指令10已超时，清理指令11却读到了迟到的10号回执，覆盖了原始超时。这条路径已用模拟接收端覆盖；仅凭旧日志无法确定真机那次故障的确切原因。新版若仍报错，会显示出错指令及期望、收到的编号；超时则单独显示等待时间和指令。先在手机点击“停止并恢复”，重新从电脑菜单1连接，并点击手机“启动接收”后再选择2测试。

APK 在内存中记录最后接收／回复编号、当前接收阶段和系统注入耗时。电脑等待回执超时后，保存关闭前后的socket统计，再通过限定为本应用服务的 `adb shell dumpsys activity service org.campusroute.android/.MockLocationService` 读取诊断；额外读取有3秒命令上限与4秒总上限。结果只显示 `CR ` 开头的诊断行，最多32行，不包含坐标、会话令牌或其他应用信息，也不写入文件。诊断不可用时保留原始超时错误。这是正常手动运行时的错误信息采集，不会自动执行地图测试。

电脑错误报告额外包含 Python版本／解释器路径、桌面版本、实际通信实现、ADB客户端与后台服务版本、USB后端、手机APK版本、上条成功回执编号与往返耗时、本条发送字节数与工作线程排队／执行时间。`before_close` 和 `after_close` 分别显示关闭前后socket收到的字节数、分块数、是否形成完整行、EOF、线程活动状态及系统错误码。计时均为相对本条指令开始的毫秒数；不打印消息正文、坐标或令牌。事件循环探针另记录本条请求期间的最大调度延迟。

第160条用户日志记录：PC在约2985毫秒时已读完91字节、形成完整行且读取线程结束，却仍进入3秒超时分支；手机处理30毫秒、无错误。旧计时采用Windows下分辨率较粗的 `monotonic`，其记录不能作为精确的到达时刻；本机Python事件循环代码也允许计时器在一个时钟分辨率内提前执行。此次修复针对提前计时与结果通知竞态，使用高精度时间戳和已完成帧兜底，保留3秒限制与完整协议校验。近3秒的通信延迟成因仍未确认，尚不能宣称整个真机问题已解决。新错误报告标识为 `PC diagnostics=3`、`threaded-socket-v3`、`timeout_policy=perf-counter-ready-first`。

APK1.1.2的 `trace_connection`／`trace_id` 关联同一条指令，记录 `request_bytes`、`read_wait_ms`（等首字节）、`frame_read_ms`（首字节到完整消息）、解码／处理／编码／写回耗时及回复字节数、写回距诊断时刻的时间。`last_failed_phase` 必须结合历史错误的连接编号、指令编号与发生时间判断；旧握手失败不再被当作当前指令失败。写入手机socket成功仍不等于电脑已收到回执。

手动复测时将两种情况分开记录：A为保留高德后台、连接后直接切回高德；B为连接后手动结束高德后台、再启动高德。每种情况发生报错时，复制从 `本次连接已中断` 开始的全部 `PC` 和 `CR` 行及清理提示即可，无需另外运行ADB命令。新版 `PC diagnostics=4` 增加 `motion_policy` 和当前请求的 `request_motion`（速度、朝向），不包含坐标或令牌。菜单状态区另显示最后已确认坐标和已发送的速度、朝向，便于对照地图显示。

第1343条用户日志记录：完整97字节回复约在3009.3毫秒到达，手机处理13毫秒，没有记录注入错误。它超过3秒截止时间，属于真实超时；当前证据不能确定延迟具体发生在手机调度、系统定位、USB／ADB或收发链路的哪一段。会话必须结束以避免串号，但无需退出控制台。本次修复未改变3秒限制，也不宣称消除了通信延迟。

`phase=applying_gps` 或 `applying_network` 且线程栈停在 `setTestProviderLocation` 才能支持对应系统调用阻塞的判断；只有服务不存在、进程退出等证据才能判断后台服务结束。阶段是诊断读取时的快照，可能已经进入清理，不能仅凭一个阶段名称认定超时原因。诊断用于缩小问题范围，是否修复需通过相同操作流程复测。

用户在荣耀 Magic5 上反馈：高德地图初次切换仍显示真实位置，重启高德后显示模拟位置，随后电脑第77条指令超时并恢复真实定位。只读检查时 CampusRoute 服务仍为前台服务，模拟定位权限为允许，未读到对应进程退出记录。高德 SDK 官方资料区分 GPS、Wi-Fi、基站与缓存结果，所以 App 重启前后的差异可能与定位来源、缓存或重新订阅有关，不能直接据此认定高德 App 的内部实现或模拟检测结果。参见[高德定位类型](https://developer.amap.com/api/android-location-sdk/guide/utilities/location-type)与[定位参数](https://developer.amap.com/api/android-location-sdk/guide/android-location/getlocation)。

测试时应同时记录电脑回执是否持续、手机接收服务是否存活，以及地图实际显示；模拟位置仍带 Android 系统标记。地图出现模拟坐标不能证明其他软件会采用该坐标。若有后台清理证据，可按[荣耀后台运行说明](https://www.honor.com/cn/support/content/zh-cn00406916/)仅对 CampusRoute 允许后台活动，再分别测试亮屏和锁屏；不要把后台管理当作已确认原因。

后续第106条回执超时的诊断为 `received_id=106 replied_id=106 last_apply_ms=18 failed_phase=none`，线程已返回等待新连接。这表示诊断读取前手机已写出106号回执；不证明该回执在3秒截止前到达电脑，也不能仅凭此判定应用被杀或定位调用阻塞。用户确认只操作手机、没有在CMD选择文字。本机实际ADB来自Unity SDK，版本32.0.0；已在项目内配置并启用官方37.0.1，使用同一手机、ADB转发和项目JSON收发代码做250条回显对照，全部通过，最长往返约16毫秒。该回显对照不调用定位API，不能替代切换／重启高德时的移动实测。电脑端超时信息现增加本机总等待与写入耗时，以便继续分辨收发延迟。

随后按用户的稳定复现步骤在真机对照：ADB37.0.1、APK1.1.1保持一致，原异步socket接收在重启高德后下一条指令222超时，电脑等待3000毫秒、本机写入约0毫秒，手机注入51毫秒且回复编号一致。仅把socket接收改到工作线程后，同一路线持续移动60秒，跨过切换和重启高德，约286米，最后收到清理确认。正式实现沿用该线程方案并保留3秒超时。这个对照支持更换接收实现，但还没有定位到Windows／ADB内部的确切机制，不把它表述为已证实的Python底层缺陷。

正式代码随后在同一手机完成120秒移动，5秒时切入高德，20秒和80秒时分别使用 `am force-stop com.autonavi.minimap` 结束并重新启动高德；两次重启后位置回执均持续，测试末尾收到清理确认并移除本次转发。用户当时确认位置点持续移动。这只能说明该轮没有复现；用户之后又在相同手动流程中复现第53条超时，所以更换电脑接收实现不能视为已解决根因。第53条报告里的 `failed_phase=handling_hello` 还可能属于更早的握手失败，新版按历史错误注明连接和指令编号。

## 荣耀 Magic5 实机验收清单

先用自有位置测试应用或地图进行验证，不把电脑端 ACK 当作独立位置回读。

| 操作 | 预期 | 当前结果 |
| --- | --- | --- |

## 上财武东路田径场

用户提供的 `custom-route.geojson` 已加入 `src/campusroute/data/sufe-wudong.geojson`，作为第7条可播放预设；地图校区列表也会显示。共209个坐标点，WGS84计算单圈约412.444米，首尾闭合。

该路线根据用户选取的足球场四角生成，最小间距2米、弯道内收10米。文件完整保留四角、尺寸、参数和 `estimated: true` 标记，并记录接收日期和原文件名。它是用户提供的参数化估算轨迹，没有声称来自OSM跑道轮廓或现场实测，也未人为缩放成400米。原待核验条目已移除。

针对用户反馈的南侧异常偏移，检查209点的数据发现相邻点间距约1.983米，南端最低纬度约31.305311860，附近坐标连续，没有额外向南的孤立坐标点。本轮保留原路线，只修正发送速度、前进方向与停止语义。该检查不能证明估算跑道与现场边界吻合，也不能确定地图显示偏移的原因；初次切入地图时真实／模拟位置跳变和南侧偏移仍需用户复测。
